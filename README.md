# نظام إدارة شركات المقاولات — Contracting ERP

نظام ERP لشركة مقاولات يغطّي خمس وحدات: المشتريات، المراسلات والتقييم، المخازن،
الحسابات، شؤون الموظفين. المرجع الكامل للمتطلّبات في [`context.md`](context.md).

> **الحالة:** `Phase 8 — الصقل` مكتملة.
> **دليل المستخدم:** [`docs/user-guide/`](docs/user-guide/index.md).

---

## المعمارية

Clean Architecture بأربع طبقات، والتبعية تتّجه للداخل فقط:

```
core  ←  application  ←  infrastructure
                      ←  presentation
```

| الطبقة           | المسؤولية                                    | ممنوع عليها                             |
| ---------------- | -------------------------------------------- | --------------------------------------- |
| `core`           | الكيانات وكائنات القيمة وقواعد العمل الخالصة | React، Supabase، config، i18n           |
| `application`    | Use Cases + Ports (واجهات مجرّدة)            | React، Supabase، infrastructure         |
| `infrastructure` | Supabase Adapters, Cloudinary, DI container  | —                                       |
| `presentation`   | React UI + Hooks                             | استيراد Supabase أو عميل قاعدة البيانات |

**هذه الحدود يفرضها ESLint** عبر `no-restricted-imports` في
[`eslint.config.js`](eslint.config.js) — أي خرق يفشل `npm run lint`.

### قواعد ملزِمة

1. **الإدخال مرة واحدة:** أي بيان مُدخَل سابقًا يُستدعى بالكود ولا يُطلب ثانية.
2. **القيود المحاسبية آلية:** كل اعتماد/تحويل يُطلق قيدًا عبر Postgres/Edge Function.
3. **لا أرقام سحرية:** كل مدة/نسبة/حد في جدول `settings`، لا في الكود.
4. **RLS أولًا:** لا شاشة قبل تأمين جدولها بسياسات تحترم الصلاحية والمشروع المعتمد.
5. **كل ميزة = migration + entity + port + use-case + adapter + mapper + hook + UI + test.**

## تخزين الملفّات

لا نستخدم Supabase Storage. كل الملفّات في **Cloudinary** برفع موقّع:

1. الواجهة تنادي use-case `UploadFile` (محقون عبر DI).
2. `CloudinaryFileStorage` ينادي Edge Function `sign-cloudinary-upload` فتعيد توقيعًا مؤقّتًا.
3. المتصفّح يرفع الملف **مباشرة** إلى Cloudinary بهذا التوقيع.
4. نخزّن في قاعدة البيانات **`public_id` و `secure_url` فقط**.

`CLOUDINARY_API_SECRET` لا يظهر في المتصفّح إطلاقًا، والحذف يمرّ عبر Edge Function.
المجلّدات مقيّدة بالجذر `erp/` ومنظّمة حسب الوحدة والمشروع: `erp/{project_id}/invoices/…`.

## الصلاحيات و RLS

خط الدفاع الأساسي هو **RLS في Postgres**، والواجهة تُخفي وتُظهر لتحسين التجربة فقط.

### دوال الصلاحيات

كلها `SECURITY DEFINER` بـ `search_path` مثبّت، فتتجاوز RLS وتمنع التكرار اللانهائي
حين تستدعيها سياسات الجداول نفسها:

| الدالة                       | الغرض                                                |
| ---------------------------- | ---------------------------------------------------- |
| `has_permission(key)`        | هل يملك المستخدم الحالي هذه الصلاحية؟                |
| `is_assigned_to_project(id)` | هل هو معتمد على هذا المشروع؟                         |
| `can_sign_project(id)`       | هل يحقّ له التوقيع على مستنداته؟                     |
| `is_active_user()`           | هل حسابه نشط؟ الموظف المعطَّل يفقد كل صلاحياته فورًا |
| `current_permissions()`      | مفاتيح صلاحياته — تقرأها الواجهة عند الدخول          |
| `current_project_ids()`      | معرّفات مشاريعه المعتمدة                             |

الواجهة تقرأ صلاحياتها من `current_permissions()` نفسها التي تستند إليها السياسات،
فلا يمكن أن يختلف ما تعرضه الواجهة عمّا يسمح به الخادم.

### قواعد مطبَّقة ومختبَرة

- الموظف يرى المشاريع المعتمد عليها فقط، ما لم يملك `project.read_all`.
- التوقيع مقصور على المشاريع المعتمدة (`can_sign` في `project_assignments`).
- الراتب في جدول `profile_salaries` منفصل — لأن RLS تعمل على مستوى الصف لا العمود،
  ففصله هو الطريقة الوحيدة لإخفائه فعليًا عمّن لا يملك `user.read_salary`.
- المستخدم يعدّل اسمه فقط؛ الكود والتصنيف والتفعيل محميّة بمُشغِّل `guard_profile_update`.
- الموظف يُعطَّل ولا يُحذف — لا توجد سياسة حذف على `profiles`.
- **أول مستخدم يُسجَّل يأخذ دور `admin` تلقائيًا** (bootstrap)، وما بعده بلا أدوار
  حتى يمنحه صاحب الصلاحية دورًا صراحةً.

### الأدوار المبدئية

`admin` (كل الصلاحيات) · `program_manager` · `project_manager` · `engineer` · `employee`

## البحث العربي في الأصناف

«بحث فوري بأي كلمة» يعني في العربية أكثر من مطابقة نصّية. المنطق كلّه في Postgres
(دالة `search_items`) فلا يتكرّر في أي عميل:

1. **تطبيع** عبر `normalize_ar()`: حذف التشكيل والتطويل، وتوحيد `أ إ آ ٱ ← ا`،
   `ؤ ← و`، `ئ ← ي`، `ة ← ه`، `ى ← ي`. فتجد «إسمنت» بكتابة «اسمنت».
2. **tsvector** (عمود `searchable` مولَّد + فهرس GIN) للكلمات الكاملة عبر الكود
   والاسم والتصنيف والوصف معًا.
3. **trigram** (`pg_trgm`) لمطابقة أجزاء الكلمات، فتجد «طوب أحمر» بكتابة «أحم».
4. **ترتيب**: مطابقة الكود أولًا، ثم `ts_rank`، ثم الاسم.

## الأتمتة المحاسبية

دفتر اليومية **سجلّ غير قابل للتعديل**: لا سياسة تعديل ولا حذف عليه، والواجهة
لا تكتب فيه إطلاقًا. القيود تُبنى على الخادم فقط:

```
الواجهة  →  use-case  →  Edge Function post-accounting-entry  →  post_accounting_entry()
                              (يتحقّق من رؤية المستند)              (SECURITY DEFINER)
```

- `post_accounting_entry` مسحوبة الصلاحية من `authenticated`، ممنوحة لـ `service_role`
  وحده — فلا مسار للترحيل إلا عبر الـ Edge Function.
- الـ Edge Function ترفض الطلب إن لم يكن الطالب **يرى المستند المصدر تحت RLS**.
- `posting_rules` تربط كل حدث بحسابَي المدين والدائن (جدول القسم 8 من المواصفات)،
  و`NULL` تعني أن الحساب يُحدَّد من المستند نفسه.
- **فهرس فريد** على `(source_type, source_id)` يمنع الترحيل المزدوج: حدث واحد ⇒ قيد واحد.
- **مُشغِّل مؤجّل** `journal_lines_balanced` يرفض أي قيد غير متوازن عند إنهاء المعاملة.
- القيد اليدوي ممنوع افتراضيًا؛ يمرّ عبر `post_manual_entry` التي تتحقّق من
  صلاحية `manual_entry.post` بنفسها.

**الأحداث المُفعَّلة الآن:** `opening_balance` فقط. باقي القواعد (عهدة، تحويل،
مستخلص، نقل مواد، سلفة) مبذورة كهيكل جاهز وتُفعَّل مع مستنداتها في مراحلها.

## سلسلة المشتريات

كل مستند يُولَّد من سابقه بدالة Postgres واحدة — تجسيد «صفر إدخال يدوي مكرّر»:

```
احتياج ──► شراء ──► تسعير ──► مقارنة ──► توريد ──► استلام ──► دفع
   │         │         │          │          │         │        │
 الحد     ‑ المتوفّر  كود المورّد  ترتيب    أسعار    مخزون   قيد صرف
 الأقصى   بالموقع    وسعره فقط   الأرخص   العرض +   الموقع+  آلي
 والمتبقّي                                  ضريبة    قيد آلي
 آليًا
```

| الدالة                                | ما تفعله                                                          |
| ------------------------------------- | ----------------------------------------------------------------- |
| `fill_material_request_line()`        | مُشغِّل يملأ `max_qty` و`prev_requested_qty` و`remaining_balance` |
| `generate_purchase_request(ids[])`    | الاحتياج − المتوفّر بالموقع، لكل مشروع على حدة                    |
| `generate_supply_order(pr, supplier)` | أسعار العرض الفائز + الضريبة من `settings`                        |
| `generate_receipt_requests(so)`       | طلب استلام لكل مشروع في أمر التوريد                               |
| `confirm_receipt(rr)`                 | يزيد `site_stock` ويغلق أمر التوريد متى اكتمل                     |
| `generate_payment_request(so)`        | حساب المورّد البنكي مستدعى تلقائيًا                               |

**التكلفة تبقى على كل مشروع** بعد الدمج: `purchase_request_lines` و`supply_order_lines`
تحملان `project_id`، فأمر توريد واحد قد يخدم عدّة مشاريع بلا خلط تكاليف.

### القيود الآلية المضافة

| الحدث               | القيد                                                   |
| ------------------- | ------------------------------------------------------- |
| `receipt_approval`  | مخزون المشروع + الضريبة **مدين** / ذمم المورّد **دائن** |
| `payment_transfer`  | ذمم المورّد + مصاريف البنك **مدين** / البنك **دائن**    |
| `material_transfer` | مخزون المستقبِل **مدين** / مخزون المُرسِل **دائن**      |

محرّك الترحيل صار **متعدّد الأسطر**: كل فرع يبني مصفوفة أسطر، فتظهر الضريبة
ومصاريف التحويل كبنود مستقلّة. أكواد حسابَي الضريبة ومصاريف البنك في `settings`
(`vat_account_code`, `bank_fee_account_code`) لا في الكود.

## محرّك سير العمل

### العدّاد داخل مواعيد العمل

أهم ما في المرحلة: **الوقت خارج الدوام لا يُحتسب**. دالتان في Postgres تحملان هذا:

| الدالة                                      | ما تفعله                         |
| ------------------------------------------- | -------------------------------- |
| `business_minutes_between(from, to, user)`  | دقائق العمل الفعلية بين لحظتين   |
| `add_business_minutes(from, minutes, user)` | موعد الاستحقاق بعد إضافة مدة عمل |

كلتاهما تقرآن `work_schedules` و`holidays`، وتتخطّيان المساء والعطلة والإجازات.
**الاستثناء الفردي يُلغي الدوام العام** لذلك اليوم لذلك الموظف [المراسلات 8].
المنطقة الزمنية من `settings.timezone`.

مثال مُختبَر: خميس 4م ← أحد 10ص = **120 دقيقة** (ساعة الخميس + ساعة الأحد)،
والجمعة والسبت لا يُحتسبان.

### دورة حياة المعاملة

```
start_transaction ──► المرحلة 1 ──► complete_step ──► المرحلة 2 ──► … ──► تمام الإنجاز
                         │                              │
                    التوزيع الآلي              الدرجة تُحتسب آليًا
                    + المدة المحفوظة            من نسبة الزمن للمدة
```

- **المدة تُدخَل مرة واحدة** [المراسلات 1، 6]: `step_duration_settings` تحفظها لكل
  موظف/نوع معاملة. الموظف أدقّ من الدور أدقّ من النوع.
- **بلا مدة ⇒ المعاملة تقف عند مدير البرنامج** [المراسلات 3] — `allocated_minutes = NULL`
  والعدّاد لا يبدأ حتى يحدّدها.
- **`duration_scope`**: `all_occurrences` تبقى، و`single` تُستهلك بعد استخدامها [المراسلات 2].
- **تعديل المدة حتى بعد الإنجاز** [المراسلات 4] يُعيد احتساب الدرجة ويُسجَّل في
  `duration_change_log` (قبل/بعد/الموظف/السبب) [المراسلات 5].
- **التوزيع الآلي** [المراسلات 23]: `workflow_steps.default_assignee_id` يوجّه كل
  معاملات النوع لموظف بعينه بدل تجميعها على المدير.

### ألوان صندوق الوارد [المراسلات 25]

عرض `transaction_inbox` يحسب اللون على الخادم:

| اللون   | الشرط            |
| ------- | ---------------- |
| 🟢 أخضر | المرحلة منجَزة   |
| 🔵 أزرق | مرّ نصف المدة    |
| 🟡 أصفر | مرّ 75٪ من المدة |
| 🔴 أحمر | انتهت المدة      |

الترتيب حسب أولوية الوصول، والعرض يُحدَّث كل دقيقة فيبقى العدّاد صادقًا.

### التقييم [المراسلات 11–18]

درجة الإنجاز تُحتسب آليًا من نسبة الزمن المستهلك إلى المدة المخصّصة، بنطاقات
**قابلة للتعديل** في `settings.completion_score_bands`:

| النسبة              | الدرجة |
| ------------------- | ------ |
| ≤ ربع المدة         | 100    |
| ≤ نصف المدة         | 75     |
| ≤ المدة (في الموعد) | 50     |
| ≤ ضعف المدة         | 25     |
| أكثر من الضعف       | 10     |

باقي البنود (سلوك، كفاءة، انضباط) تُقيَّم يدويًا، و**الأوزان تختلف حسب فئة الموظف**
(إداري: إنجاز 70٪ · مهندس: إنجاز 20٪ وكفاءة 40٪). عرض
`employee_evaluation_summary` يجمعها بالأوزان ويحسب **الترتيب** داخل كل فترة،
مع استثناء من في `evaluation_exclusions` [المراسلات 16].

### الخصوصية [المراسلات 19]

- تفاصيل المعاملة للموقّعين فقط (RLS عبر `is_transaction_participant`).
- `search_transactions_brief` تُظهر الرقم والنوع والحالة لغير الموقّعين — بلا موضوع
  ولا مراحل ولا ملاحظات.
- ملاحظة المدير تُحجب في العرض عمّن لم تُخصَّص له.

### الخطابات الآلية [المراسلات 10]

`auto_letter_rules` + Edge Function `run-auto-letters` بجدول زمني. الخطاب يصل
الوارد **كمعاملة رسمية لها مدة وعدّاد** لا كإشعار عابر. الدالة محميّة بسرّ مشترك
(`CRON_SECRET`) لأن مُشغِّلها جدول لا مستخدم.

## المخازن

سلسلة المادة متّصلة من أولها لآخرها بلا إدخال مكرّر:

```
استلام المشتريات  →  site_stock  →  عهدة المندوب  →  تنزيل على منشأة
                                    (مخزن فرعي)      (بصوره + إشعار فوري)
```

كل تغيير رصيد يقع في **دالة Postgres واحدة** (`issue_stock_to_mandoub`،
`return_mandoub_stock`، `record_facility_consumption`): تفحص الصلاحية والمشروع
المعتمد، تقفل الصف (`for update`)، تنقص رصيدًا وتزيد آخر، تكتب الأثر في
`stock_movements`، وتُطلق الإشعار — كل ذلك ذرّيًا. لا سياسة كتابة على
`mandoub_stock` إطلاقًا، فلا مسار لتغيير رصيد يتجاوز هذه الدوال.

### الوزن النسبي وكشف الهدر [المخازن 9]

منشأتان في حي واحد قد تختلفان حجمًا، فمقارنة الكميات المجرّدة ظالمة. لكل منشأة
`weight` (مساحة/عدد وحدات — يحدّده المستخدم)، والمقارنة تجري على:

```
الاستهلاك لكل وحدة وزن  =  الكمية ÷ وزن المنشأة
نسبة الانحراف           =  ذلك ÷ متوسط المشروع لنفس الصنف
هدر                     =  النسبة > waste_deviation_ratio  (إعداد، لا رقم في الكود)
```

مثال محسوب فعليًا: منشأتان استهلكتا 20 شيكارة، بوزنَي 10 و40 ⇒ النسبتان 1.6×
و0.4× ⇒ الصغيرة تُعلَّم هدرًا عند عتبة 1.5.

| العرض / الدالة                   | التقرير                                 |
| -------------------------------- | --------------------------------------- |
| `facility_waste_report`          | الهدر بالوزن النسبي لكل منشأة وصنف      |
| `project_consumption_summary`    | مقارنة المشاريع (الوزن يُجمع مرة واحدة) |
| `supervisor_consumption_summary` | مقارنة المشرفين وكم تنزيل صاحبته صور    |
| `consumption_trend(months)`      | التراكمي 3/6/12 شهرًا                   |

كلها `security_invoker` فتسري عليها سياسات الجداول الأصلية: لا يرى أحد مشروعًا
غير معتمد له حتى داخل تقرير.

### الإشعار الفوري [المخازن 18، 19]

جدول `notifications` عام لكل الوحدات، **بلا سياسة كتابة**: الإشعار يُولَد من
`notify_users()` داخل دوال المالك عند الحدث نفسه، ويقرأ كل مستخدم إشعاراته وحده.
المُرسِل لا يُشعر نفسه. الجرس في الشريط العلوي يُحدَّث دوريًا فيصل الخبر بلا تحديث
صفحة.

### المعدّات

الحركة هي مصدر الحقيقة: `move_equipment` تُغلق الحركة المفتوحة وتفتح أخرى ويتبعها
`current_project_id` وحالة المعدّة آليًا (فهرس فريد يمنع وجودها في مشروعين معًا).
`release_equipment` تُخليها وتعلنها **شاغرة** وتُشعر أصحاب صلاحية المعدّات — فلا
يُستأجر ما هو متاح. الصور ومستندات المعدّة مراجع Cloudinary كالمعتاد.

## المستخلصات والعهد

### المستخلص: إدخال واحد هو الكمية

سعر البند وكميته التعاقدية يُدخلان مرة واحدة في `contractor_boq_contracts`،
ثم لا يسألهما مستخلص بعد ذلك. `generate_extract(project, contractor)` تبني
المستخلص التالي كاملًا على الخادم:

```
الرقم التالي في العقد (1 … الختامي)
  + أسطر بنود العقد بأسعارها وحدودها (لقطة لا تتأثّر بتعديل العقد لاحقًا)
  + الكميات السابقة = مجموع المعتمد قبله
  ⇒ لا يُدخل المهندس إلا كمية هذا المستخلص
```

مُشغِّل `guard_extract_line` يرفض أي كمية تتجاوز `max_qty − prev_qty`، ويرفض
تعديل أسطر مستخلص معتمَد. ولا يُفتح مستخلص جديد قبل اعتماد سابقه، وإلا فسدت
الكميات السابقة.

### الاستقطاعات: قرار صاحب البرنامج لا قرار الكود

`deduction_types` جدول قابل للتعديل بالكامل (نسبة، حساب دائن، تفعيل، ترتيب).
البذور الافتراضية للبدء فقط: ضمان أعمال 5٪، خصم من المنبع 1٪، وتأمينات
واسترداد دفعة مقدّمة معطّلان حتى يُفعّلهما صاحب البرنامج.

`approve_extract` يلتقط **لقطة** من الإعداد وقت الاعتماد في `extract_deductions`،
فتعديل النسبة لاحقًا لا يمسّ مستخلصًا معتمَدًا. القيد يُبنى من اللقطة:

```
مستخلص 40,000 (ضمان 5٪، ضريبة 1٪):
  5101 تكلفة التنفيذ      مدين  40,000
  2103 محتجزات الضمان            دائن   2,000
  2202 ضرائب مستحقّة             دائن     400
  2102 ذمم المقاولين             دائن  37,600  ← طلب الدفع بهذه القيمة
```

المستخلص **الختامي** يردّ ما احتُجز في سابقيه: `2103` يصير مدينًا بالمردود
ويزيد صافي المستحقّ بالقدر نفسه، والقيد يبقى متوازنًا.

### كشف تكرار الفواتير [الحسابات 29]

ثلاث طبقات، كلها في قاعدة البيانات لا في المتصفّح:

1. **التطبيع**: `normalize_doc_no()` يوحّد الأرقام العربية واللاتينية ويطبّع
   الحروف العربية ويحذف الفواصل — فـ«١٢٣/أ» و«123 ا» فاتورة واحدة.
2. **المُشغِّل**: عند كل إدخال أو تعديل، يبحث عن فاتورة بنفس (الرقم + القيمة)،
   والأقدم هو الأصل دائمًا فلا يتبادل صفّان متطابقان الاتّهام.
3. **إعادة المسح قبل الاعتماد**: `approve_custody` تستدعي
   `rescan_custody_duplicates` ثم **ترفض الاعتماد** ما دامت هناك فاتورة مكرّرة
   لم تُراجَع — فلا يمرّ تكرار حتى لو أُدخلت الفواتير دفعة واحدة.

البلاغ يذهب لأصحاب صلاحية `invoice.review` **لا لمن أدخل الفاتورة**، عبر جدول
`notifications` نفسه. والفاتورة المرتجعة تُنقل إلى «العهدة الحمراء» — وعاء
مرتجعات يُنشأ تلقائيًا لكل (مشروع + صاحب عهدة) [الحسابات 30]، ولا يدخل إجمالي
العهدة ولا يُعتمد.

### المسح الضوئي (OCR) — مُعين لا حَكَم

`Tesseract.js` يعمل **في المتصفّح** (عربي + إنجليزي، بلا خدمة خارجية ولا تكلفة):
الصورة لا تغادر جهاز المستخدم للمسح، والنص المستخرج يملأ رقم الفاتورة وقيمتها
ليراجعهما المستخدم قبل الحفظ. الحكم بالتكرار يبقى على الحقول المحفوظة في
قاعدة البيانات، فلا تُفلت فاتورة بجودة مسح رديئة ولا يُلتفّ على الكشف بتعديل النص.
المحرّك خلف منفذ `IOcrReader`، فتبديله لا يمسّ الواجهة.

### الدفعات المقدّمة والضمانات

- الدفعة المقدّمة: `1303 دفعات مقدّمة` **مدين** / `2102 ذمم المقاولين` **دائن**،
  وتُسترد من المستخلصات باستقطاع `advance_recovery` بعد تفعيله.
- الضمانات: `expiring_guarantees` تعرض الأقرب انتهاءً بالأيام المتبقّية،
  و`notify_expiring_guarantees()` تُشغَّل مع الوظيفة المجدولة فتعلّم المنتهي
  وتُشعر أصحاب `guarantee.manage` قبل الموعد بمدة من `settings`
  (`guarantee_alert_days`).

### القيود الآلية المضافة في هذه المرحلة

| الحدث              | القيد                                                        |
| ------------------ | ------------------------------------------------------------ |
| `extract_approval` | تكلفة التنفيذ **مدين** / الاستقطاعات + صافي المقاول **دائن** |
| `custody_approval` | مصروفات العهدة **مدين** / ذمة صاحب العهدة **دائن**           |
| `advance_payment`  | دفعات مقدّمة **مدين** / ذمم المقاولين **دائن**               |

محرّك الترحيل صار يتحقّق من **توازن القيد** قبل الكتابة، فلا يُسجَّل قيد غير
متوازن مهما كان مصدره.

## شؤون الموظفين

### اليوميات: ثلاث قواعد في قاعدة البيانات لا في الواجهة

| القاعدة                                | كيف طُبِّقت                                          |
| -------------------------------------- | ---------------------------------------------------- |
| عامل واحد ليوم واحد في مشروع واحد [16] | `unique (worker_id, work_date)` — قيد لا مجرّد تحقّق |
| لا تسجيل بعد الموعد إلا بصلاحية [17]   | مُشغِّل يقارن الساعة بـ `attendance_cutoff_time`     |
| قيمة اليوم بحسب حالته [3]              | `attendance_day_values` في `settings`                |

قيم البدء: حاضر **1**، مريض **0.5**، غياب بإذن **−1**، بدون إذن **−2** — كلها
قابلة للتعديل، وتغييرها يغيّر «اليوميات المستحقّة» في كل التقارير فورًا.

**اقتراح أسماء الأمس [2]:** `suggest_attendance(project, date)` تُعيد عمّال آخر
يوم عمل مسجَّل للمشروع مع حالتهم وهل سُجّلوا اليوم. الشاشة تفتحهم مؤشَّرين
بحضور، فيزيل المستخدم الغائب أو يغيّر حالته — لا يعيد كتابة الكشف كل صباح.

**البحث عن العامل [2]:** بالاسم ولو كُتب شاذًّا (`normalize_ar`)، أو بالكود، أو
برقم البطاقة — والأرقام العربية واللاتينية سواء (`normalize_doc_no`).

### «كم يومية كلّفني المشروع»

عرضان لا واحد، والفرق بينهما صلاحية:

- `project_labor_days` — الأيام والأعداد، يراها كل من يرى اليوميات.
- `project_labor_cost` — التكلفة بالمال، تمرّ عبر `profile_salaries` فلا تظهر
  إلا لمن يملك `user.read_salary`. الإخفاء بالبيانات لا بالـ CSS.

### الخدمة الذاتية [7]

العامل ملف (`profiles`) كسائر الموظفين — لأن حسابه شرط الخدمة الذاتية، ولأن
دفترين للأشخاص يكسران «الإدخال مرة واحدة». وشاشة «خدمتي» تعمل **بلا أي دور**:
سياسات RLS تسمح لصاحب الصف برؤيته:

```sql
using (worker_id = (select auth.uid()) or public.has_permission('loan.read'))
```

فيرى يومياته وسلفه ودرجته، ويطلب سلفة لنفسه بحالة «مطلوبة» فقط — ولا يستطيع
اعتمادها ولا تعديل حالتها.

### السلفة ⇒ قيد آلي

`decide_loan` عند الاعتماد تولّد `payment_request` للعامل، فيمرّ بآلة التحويلات
البنكية نفسها من المرحلة 3، ويُسجَّل قيده: **ذمم العامل (1301) مدين / البنك
(1101) دائن** — وهو سطر «صرف سلفة» في جدول القسم 8 حرفيًا.

### الأجر والتقييم

- الأجر لا يتغيّر بلا أثر: `change_worker_salary` تكتب `profile_salaries`
  وتسجّل في `salary_changes` (قبل/بعد/من/لماذا) في معاملة واحدة.
- **معدّل الإنتاج [10]:** النسبة = الدخل المنسوب ÷ تكلفة يومياته (محسوبة من
  الحضور والأجر)، والدرجة من شرائح `production_score_bands` القابلة للتعديل.
- بنود السلوك والانضباط والجودة والفنيات [11] تُقيَّم بمحرّك التقييم نفسه من
  المرحلة 4 بعد إضافة فئة «عامل» وأوزانها.
- التوصيات (`worker_recommendations`) مقصورة على `worker.recommend` — لا يراها
  العامل ولا المشرف.

### ترحيل كشف البنك

Edge Function `import-bank-statement`: يطابق كل سطر برقم طلب الدفع **وقيمته
معًا**، فيعلّمه محوَّلًا ويُسجّل قيده. فيه وضع **تجربة بلا ترحيل** (`dryRun`)
يُظهر ما سيُطابَق وما سيُتخطّى قبل أي كتابة، وشرط `neq('status','transferred')`
يمنع سباقًا مع تحويل يدوي جارٍ، فلا يُرحَّل تحويل مرتين.

## التقارير الشاملة

تقارير الوحدات تجيب عن أسئلة وحدتها. هذه تجيب عمّا جوابه موزّع على أكثر من
وحدة، ولهذا لم يكن مكانها أي مرحلة سابقة.

| التقرير             | يجمع من                                               |
| ------------------- | ----------------------------------------------------- |
| تكلفة المشاريع      | أوامر التوريد + العهد + المستخلصات + الدفعات المقدّمة |
| أرصدة الأطراف       | دفتر الأستاذ — لا مستندات الوحدات                     |
| القيود اليدوية      | القيود غير الآلية ومن رحّلها [الحسابات 17]            |
| المعاملات المتأخّرة | عدّاد صندوق الوارد نفسه                               |
| الأصول غير المستلمة | الأرشيف [المراسلات 22]                                |
| المدد المعدّلة      | سجل تغيير المدد [المراسلات 5]                         |
| تردّد الأقسام       | مرور المعاملة على القسم نفسه [المراسلات 24]           |

### الصلاحية داخل العرض لا حوله

المفتاحان `report.read` (تشغيلي) و`report.financial` (مالي) لا يُفحصان في
الواجهة ولا في المستودع، بل **داخل شرط `where` في العروض نفسها**:

```sql
create or replace view public.project_cost_summary
with (security_invoker = true) as
select … from public.projects p
…
where public.can_read_financial_reports();
```

فمن يقرأ العرض مباشرةً بلا الصلاحية يستلم صفر صفوف من قاعدة البيانات. وبما
أن العروض `security_invoker`، تبقى سياسات الجداول الأصلية سارية فوق ذلك:
لا يرى الموظف في التقرير ما لا يراه في شاشته.

### لماذا تكلفة العمالة خارج تقرير التكلفة

مصدرها `profile_salaries` المحميّة بـ RLS. ضمّها كان سيُنقص الإجمالي **صامتًا**
لمن لا يملك `user.read_salary` — ورقم ناقص بلا تحذير أخطر من رقم غائب.
مكانها العرض المستقل `project_labor_cost`.

## النسخة الاختبارية [الحسابات 1]

`seed_demo_data()` و`clear_demo_data()` خلف صلاحية `demo_data.manage`، وواجهتهما
بطاقة في شاشة الإعدادات.

- **الأكواد كلها `DEMO-`** فتُميَّز في أي شاشة.
- **القيود تُرحَّل بـ `post_accounting_entry` نفسها** لا بإدراج مباشر في دفتر
  اليومية — وإلا تدرّب الموظف على نظام غير النظام.
- **كل صف مُولَّد مسجَّل في `demo_data_objects`**، والحذف يمرّ على ذلك السجل
  وحده. صف حقيقي كوده يبدأ بـ `DEMO-` لا يُمَسّ، لأنه ليس في السجل.

| ما تغيّر                    | الأثر                                                |
| --------------------------- | ---------------------------------------------------- |

الفهارس **ليست كل ما اقترحه المدقّق** (١٢٧). الفهرس ليس مجانيًا: كل إدراج
وتحديث يدفع ثمنه. فاستُبعدت أعمدة التدقيق (`created_by`, `approved_by` …) لأنها
تُكتَب دائمًا ولا يُبحث بها، واستُبقي منها ما تجمّع عليه التقارير فعلًا.

**معروف ولم يُعالَج:** ٦٣ تحذير `multiple_permissive_policies` — سياسات `for all`
تغطّي `SELECT` بجانب سياسة `select` مخصّصة، فتُقيَّم الاثنتان. معالجتها تعني
إعادة كتابة ٦٠+ سياسة أمنية مختبَرة مقابل مكسب أداء هامشي، فأُجّلت عمدًا.

## النشر على Vercel

التطبيق **SPA**: الخادم يخدم `index.html` وحدها، والتوجيه كلّه في المتصفّح.
بلا إعادة كتابة، أي تحديث للصفحة على مسار مثل `/reports` يطلب من Vercel ملفًّا
لا وجود له فيردّ **404**. لذلك [`vercel.json`](vercel.json):

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

قواعد `rewrites` تُطبَّق **بعد** فحص نظام الملفّات، فملفّات `assets/` و`favicon.svg`
تُخدَم كما هي ولا يبتلعها التحويل.

| الإعداد       | القيمة          |
| ------------- | --------------- |
| Framework     | Vite            |
| Build Command | `npm run build` |
| Output        | `dist`          |

ومتغيّرات البيئة في **Project Settings ← Environment Variables** — الأربعة كلها
مطلوبة وإلا فشل الإقلاع برسالة صريحة من `src/config/env.ts`:

```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
VITE_CLOUDINARY_CLOUD_NAME
VITE_CLOUDINARY_API_KEY
```

> `SUPABASE_SERVICE_ROLE_KEY` و`CLOUDINARY_API_SECRET` **لا يوضعان في Vercel**.
> مكانهما أسرار Edge Functions في Supabase — أي متغيّر يُضاف هنا بلا بادئة
> `VITE_` لا يصل المتصفّح، لكن وضع سرّ في إعدادات الواجهة عادةٌ سيّئة ابتداءً.
